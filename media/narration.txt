Analytics runs on columns. Rename one column upstream and nothing crashes. The queries below it keep running, quietly returning wrong numbers, and nobody notices for days. That is schema drift.

DataHub is the open source catalog underneath. Our agent reads it through M C P, the standard way an agent calls a tool server. Four capabilities do the work: schema metadata, column level lineage, incidents, and catalog write back.

So let's cause it on purpose. One click renames order placed at to order created at in the live catalog. This is the real catalog, not a copy. The drift is live, and nobody downstream was told.

Capability one: schema metadata. The agent reads the live schema from DataHub and compares it with the committed baseline. One row differs. Same type, same position, new name. It infers a rename.

Now watch the agent work. Every violet chip on the right is a real M C P call to DataHub. Search, to find the table. List schema fields, for its exact column names. Get lineage, for the changed column, downstream. Then get lineage paths between, four times, to confirm each path.

Capability two, the one that matters: column level lineage. DataHub records which downstream column each column feeds. So the agent asks what reads this column, not what touches this table.

Three answers, not two. Three files, in amber, read the changed column and must be patched. Two, in blue, are downstream but read order date, a copy renamed one hop up, so they need nothing. Seven, in grey, are correctly untouched.

Every skip carries evidence. This model really is downstream, but it reads columns like order I D, quantity and unit price. None is on the changed column's path. Listing everything downstream is easy. Knowing what actually breaks is not.

The language model never writes code. Patches come from SQL Glot, which edits the query's syntax tree, so only the changed tokens move. Four files. The model's job is the explanation.

Then a hard gate. Every column reference must resolve. Twenty three of twenty three: fifteen against live DataHub schemas, six against the repaired schema this change creates, and two inside the query itself. One failure blocks the pull request.

It opens a real pull request, a proposed code change for a human to review, carrying the lineage path from the changed column to every file it touched.

Capabilities three and four go back into DataHub. Corrected fine grained lineage. The repaired column documented. Tags on every repaired asset. An incident raised through the incidents A P I and moved to triage. And the run itself recorded.

The next engineer opens the catalog and finds the answer already there. Column level lineage to find what truly broke. Deterministic edits to fix it. And DataHub as the source of truth at both ends.
