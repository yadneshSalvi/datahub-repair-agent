Every company's data lives in hundreds of tables, wired together by pipelines nobody fully remembers. DataHub is an open source catalog that keeps that map: every table, every column, every pipeline.

Here is the failure it cannot fix on its own. Someone upstream renames one column. Nothing crashes. The pipelines below keep running, quietly producing wrong numbers, and nobody notices for days.

So let's break it on purpose. One change to the live catalog: in the orders table, order placed at becomes order created at. Now the catalog shows drift, and nobody downstream was told.

Here is the detector's evidence. On the left, the columns DataHub had on record. On the right, what is in the warehouse now. Every row matches but one.

Now the agent goes to work. Watch the timeline on the right. Those violet chips are its live questions to DataHub, asked through M C P, the connector that lets an agent query a catalog directly. Search the catalog. List this table's columns. Trace this column downstream. Every answer comes from the catalog, not a text search.

Here is the result, and it is the heart of this project. Column level lineage maps exactly which downstream code reads this one column, not merely which tables connect.

So you get three answers, not two. Three files, in amber, genuinely read the changed column and need fixing. Two, in blue, read a renamed copy made upstream, so they need nothing. Seven, in grey, are correctly left alone.

Click one of the seven and it shows its work. It really does sit downstream, but it reads columns like order I D, quantity and unit price, and not one of them is the column that changed. Anyone can list everything downstream. Knowing what genuinely breaks is the hard part.

The fixes are surgical. Here's the same file, before and after. Only the tokens that changed have moved. The rewrite is done by SQL Glot, a parser that edits the syntax tree directly. The model never writes code. It writes the explanation.

And nothing ships until every column reference checks out. Twenty three of twenty three resolved, and it shows where each answer came from: live DataHub schemas, the repaired schema, or the query itself. One unresolved reference blocks the whole patch.

Then it opens a real pull request, a proposed code change sent to a person to review, carrying the lineage path from the changed column to every file it touched.

Finally it writes the repair back into DataHub, so the catalog is true again: lineage corrected, the column documented, and an incident logged for sign off. The next engineer, or the next agent, inherits it.
