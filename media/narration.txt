An upstream team renames a column. Nothing errors. Downstream models keep running and quietly produce wrong numbers, and you find out days later from someone looking at a bad dashboard.

So let's break it, the way it actually happens. In DataHub, order placed at becomes order created at, in the real catalog. Nobody told the downstream teams.

The agent reads DataHub through the M C P server. You can watch the calls land: search, schema fields, lineage on the changed column, captured queries. This is not grep. Every conclusion is grounded in the catalog.

Column-level lineage gives three answers, not two. Three files genuinely reference the changed column and need a patch. Two marts sit in the blast radius but read an alias created upstream, so they need no change at all. And seven models are correctly skipped.

Click a skipped model and it tells you why: exactly which columns it does consume, and that none of them sit on the changed column's path. Anything can list everything downstream. Knowing what genuinely breaks is the hard part.

Patches are surgical. Sqlglot locates the references, and only the changed tokens move. The language model never writes code. It writes the explanation.

Then every column reference is resolved before anything ships. Twenty-three of twenty-three, against the catalog. One unresolvable reference blocks the whole patch. The gate is enforced, not advisory.

It opens a real pull request, carrying the column lineage path as evidence and the reason each unaffected model was left alone.

Then it writes the repair back: corrected column lineage, the renamed column documented, tags, an incident raised for review. The next engineer, or the next agent, inherits all of it.

Column-level lineage for impact. A S T rewrites for correctness. The catalog as the source of truth on both sides.
